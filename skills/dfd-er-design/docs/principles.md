# หลักการออกแบบ: ข้อมูลต้องมีที่มาที่ไป

เอกสารนี้คือ "ตรรกะ" ของ DFD และ ER ส่วนรูปแบบการวาดดูที่ `dfd-style.md` และ `er-style.md`

## 1. หลักการหลัก

1. **ข้อมูลต้องถูกสร้างก่อนถูกใช้**
   - ข้อมูลทุกตัวที่ process อ่าน ต้องมี process ที่บันทึก (Create) ไว้ก่อนแล้ว
   - ห้ามมี process ที่อ่านข้อมูลซึ่งไม่มีใครสร้าง
2. **ข้อมูลทุกตัวต้องมีต้นทาง (source) และปลายทาง (destination)**
   - ต้นทาง: External Entity ส่งเข้ามาผ่าน process เท่านั้น
   - ปลายทาง: เก็บลง Data Store หรือส่งออกให้ External Entity เป็นรายการ รายงาน หรือการแจ้งเตือน
   - ข้อมูลทุกตัวในรายงานต้องย้อนกลับไปหา process ที่สร้างมันได้
3. **เรียง process ตามลำดับการเกิดข้อมูล: Master → Transaction → Report**
   - ก่อน: ข้อมูลหลัก (Master) เช่น อุปกรณ์ พนักงาน ทีม โซน
   - ถัดมา: ค่าที่ต้องกำหนดไว้ใช้ภายหลัง เช่น เกณฑ์ KPI (ใส่ก่อน process ที่ใช้ค่านั้น)
   - ถัดมา: ธุรกรรม (Transaction) ที่ใช้ข้อมูลหลัก เช่น แจกจ่าย ใช้งาน ปรับสถานะ
   - ท้ายสุด: ติดตาม ออกรายงาน แจ้งเตือน ซึ่งอ่านข้อมูลทั้งหมดข้างบน
   - ถ้า process B ต้องใช้ข้อมูลจาก process A แปลว่า A ต้องมาก่อน B
   - ถ้าตาราง X มี FK แบบ NOT NULL ไปตาราง Y แปลว่า process ที่สร้าง Y ต้องมาก่อน process ที่สร้าง X
     (`tools/check_spec.py` เตือนให้อัตโนมัติ; ถ้าอาจารย์กำหนดลำดับเองให้ทำตามอาจารย์ แล้วอธิบายใน Process Description)
4. **ทุก Data Store ต้องตอบได้ 3 ข้อ**: process ไหนสร้าง (C), process ไหนอ่าน/แก้/ลบ (R/U/D), ข้อมูลไปจบที่ไหน
   ถ้าตอบไม่ได้ แปลว่าขาด process หรือ store นั้นไม่จำเป็น

## 2. สถานะเป็นข้อมูล ไม่ใช่ process

- "ส่งซ่อม" "ชำรุด" "รอแจกจ่าย" คือ **ค่า** ในคอลัมน์ status หรือแถวในตาราง lookup (เช่น `spare_statuses`)
- ใช้ process เดียว เช่น "ปรับสถานะอุปกรณ์" เป็นตัวเปลี่ยนค่า
- ห้ามแตก process ทีละสถานะ เช่น "ส่งซ่อม" "รับคืน" "ชำรุด" เป็นกล่องแยกกัน เว้นแต่ขั้นตอนนั้นมีผู้กระทำ ข้อมูลเข้า หรือ store ต่างกันจริง

## 3. ค่าที่มีคนกำหนด ต้องมี process และ store ของตัวเอง

- เช่น เกณฑ์ KPI ระยะเวลาสูงสุด อัตรา หรือเงื่อนไขแจ้งเตือน
- สร้าง process "กำหนดเกณฑ์ ..." ที่บันทึกลง store ของตัวเอง (เช่น D8 ข้อมูลเกณฑ์ KPI) เพื่อรู้ว่าใครกำหนด ค่าเท่าไร มีผลเมื่อไร
- process ที่ใช้ค่านั้น (ติดตาม/แจ้งเตือน) ให้ **อ่าน** จาก store นี้ ห้ามฝังค่าไว้ในชื่อ process

## 4. ประวัติ (history) เก็บเฉพาะที่จำเป็น

- ทำตาราง log เมื่อสิ่งนั้นเปลี่ยนได้ **และ** ต้องรู้ย้อนหลัง เช่น หัวหน้างานย้ายทีม อุปกรณ์เปลี่ยนสถานะ
- เก็บแค่: ค่าก่อนหน้า ค่าใหม่ ผู้ทำ เวลาที่เปลี่ยน (เช่น `prev_team_id`, `new_team_id`, `changed_at`)
- ไม่ต้องมีวันเริ่ม/วันสิ้นสุด ถ้าไม่มีรายงานใดใช้
- สิ่งที่ไม่เปลี่ยน ไม่ต้องเก็บประวัติ

## 5. ธุรกรรมแยกตารางของตัวเอง

- การแจกจ่าย การใช้งาน การเปลี่ยนอุปกรณ์ แต่ละอย่างคือ "เหตุการณ์" ต้องบันทึกว่าใคร ทำอะไร กับอะไร เมื่อไร
- อย่ารวมไว้ในตาราง master (เช่น อย่าใส่ "วันที่แจก" ไว้ในตารางอุปกรณ์แทนตารางการแจกจ่าย)

## 6. กฎของ DFD (ตรรกะ)

- **Context Diagram**: process เดียว (เลข 0 = ตัวระบบ) + External Entity ทุกตัว + ข้อมูลหลักเข้าออก ไม่มี Data Store
- **Level 1**: ทุก process เรียงตามข้อ 1.3 ชื่อ process เป็นวลีกริยา; ชื่อ store และ data flow เป็นคำนาม
- **Level 2**: ทำเฉพาะ process ที่มีหลายขั้นตอนต่อกัน มีหลายผู้กระทำ หรือเขียนหลาย store; process ที่บันทึก/แก้ไขขั้นเดียวไม่ต้องแตก
- **Balancing**: ข้อมูลที่ขอบของ Level 2 (entity + store) ต้องตรงกับ process แม่ใน Level 1 ชื่อและเลขเดียวกัน
  (Context ต้องตรงกับผลรวมของ Level 1 ฝั่ง entity — generator สร้าง Context จาก Level 1 ให้อัตโนมัติจึงสมดุลเสมอ)
- **ข้อห้าม**: Black hole (มีแต่เข้า), Miracle (มีแต่ออก), Gray hole (ข้อมูลออกสร้างจากข้อมูลเข้าไม่ได้),
  Entity↔Store ตรง, Store↔Store ตรง, Entity↔Entity ตรง
- ระหว่างคู่เดียวกัน **ทิศละ 1 ลูกศร** ถ้ามีหลายข้อมูลให้รวมชื่อ (เช่น "ข้อมูลรับคืน/ส่งซ่อม")

## 7. ER มาจาก Data Store

1. Data Store แต่ละตัว = ตาราง 1 ตารางขึ้นไป (map ไว้ใน `store_tables`) ห้ามมีตารางที่ไม่มี store และ store ที่ไม่มีตาราง
2. แยกเรื่องที่ต่างกันออกจากกัน (employees / users / roles, teams / zones, product_types / products / spares) อย่ารวมเพื่อให้ตารางน้อย
3. Cardinality มาจากกฎธุรกิจจริง ถามให้ชัดก่อน ("1 ทีมมีได้หลายโซนไหม 1 โซนอยู่ได้กี่ทีม") แล้ววาง FK ไว้ฝั่ง "หลาย"
4. FK ที่ว่างได้ (nullable) = ฝั่ง parent เป็น "ศูนย์หรือหนึ่ง"
5. ระหว่าง 2 ตาราง มีเส้นเดียว แม้มี FK หลายตัว (เช่น `team_supervisor_logs.prev_team_id` และ `new_team_id` → `teams`) อธิบาย FK ที่เหลือใน Data Dictionary
6. Data Dictionary ต้องตรงกับ ER ทุกฟิลด์ และสร้าง SQL DDL จากไฟล์เดียวกัน (`templates/sql/dd_to_sql.py`) เพื่อให้ DD = ER = SQL

## 8. ถามแทนการเดา

เมื่อกฎธุรกิจไม่ชัด ให้ถามผู้ใช้ เช่น "1 X มีได้หลาย Y ไหม" "ต้องเก็บเป็นประวัติไหม" "ใครเป็นผู้กำหนดค่านี้"
"ใครเป็นผู้รับรายงานนี้" อย่าเพิ่ม process ตาราง หรือฟิลด์ที่ไม่มีใครใช้

## 9. ข้อมูลที่ต้องขอจากผู้ใช้ก่อนเริ่ม

- ชื่อโครงการ (ไทย/อังกฤษ), ผู้ใช้และบทบาท, ขั้นตอนการทำงานปัจจุบันทีละขั้น
- ข้อมูลที่ต้องบันทึก, รายงาน/การแจ้งเตือนที่ต้องการ และผู้รับ
- กฎหรือข้อจำกัด (KPI, สิทธิ์), หน่วยงานภายนอกระบบ (เช่น คลัง)
- ข้อเสนอแนะของอาจารย์/กรรมการ และไฟล์ตัวอย่างสไตล์ของอาจารย์ (ถ้ามี)

## 10. สิ่งที่ต้องส่งมอบ (ลำดับนี้)

1. รายการ External Entity และข้อมูลที่แต่ละตัวส่งเข้า/รับออก
2. รายการ Data Store (D1, D2, ...) เก็บอะไร process ไหนสร้าง process ไหนใช้
3. process ของ Level 1 ตามลำดับ พร้อมข้อมูลเข้า ข้อมูลออก store และเหตุผลของลำดับ
4. process ที่ต้องทำ Level 2 และเหตุผล
5. ER: ทุกตาราง PK/FK ความสัมพันธ์และ cardinality
6. CRUD matrix และรายการปัญหาที่พบตอนตรวจ
7. คำถามที่ผู้ใช้ต้องตอบ
