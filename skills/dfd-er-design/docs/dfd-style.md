# DFD style (Context, Level 1, Level 2): ค่าที่ใช้จริง

ทุกค่ามาจาก `templates/generator` (draw.py, lay.py, vsdx.py, d_*.py) ที่สร้างรูปในรายงานจริง
**อย่าเดาค่าใหม่ ให้คัดลอก template แล้วแก้ spec** ถ้าต้องเปลี่ยนค่า ให้แก้ใน spec (`layout`) ไม่ใช่ในโค้ด

## 1. หน่วยและฟอนต์

| รายการ | ค่า |
|---|---|
| หน่วย layout | นิ้ว (in), แกน y ชี้ลง (ใน vsdx แปลงเป็นแกน Visio ให้อัตโนมัติ) |
| ฟอนต์ในแผนภาพ | **TH Sarabun New** (Font, ComplexScriptFont, AsianFont = TH Sarabun New, LangID th-TH) |
| ขนาดฟอนต์ | ใน spec เป็น "layout pt" แล้วคูณ **K = 1.5295** เป็นขนาดจริงของ TH Sarabun New (ฟอนต์นี้ตัวเล็กกว่าฟอนต์ทั่วไป) |
| ระยะบรรทัด | `LINE(pt) = pt / 72 × 1.22` นิ้ว ต่อบรรทัด × 1.05 |
| สีตัวอักษร/เส้น | ดำ `#000000` ทั้งหมด |
| ฟอนต์ในตัวรายงาน | TH SarabunPSK (คนละตัวกับในแผนภาพ ตั้งใจ ไม่ต้องแก้) |

|---|---|---|---|

| Context: data flow label | 16 | 24.5 pt | ปกติ |
| L1/L2: ชื่อ process (PPT) | 16 | 24.5 pt | ปกติ, เลข process ตัวหนา |
| L1/L2: ชื่อ store (SPT) | 15 | 22.9 pt | ปกติ, รหัส D1.. ตัวหนา |
| L1/L2: entity | 16 | 24.5 pt | ปกติ |
| L1/L2: data flow label (LP) | 15 | 22.9 pt | ปกติ |

## 2. หน้ากระดาษ

- **1 แผนภาพ = 1 หน้า Visio = 1 รูป** ห้ามแบ่ง Level 1 เป็นหลายหน้า
- canvas เริ่มต้น: Context 12.4×10.2, Level 1 13×20, Level 2 13×12 (นิ้ว) แล้ว `fit()` ตัดขอบให้เหลือ margin **0.12 in** รอบรูป
- PageScale = DrawingScale = 1 in (1:1)
- ขนาดหลัง fit ของตัวอย่าง: Context 12.44×7.49, L1 11.64×21.05, L2-P6 12.49×7.81, L2-P8 12.51×9.17 นิ้ว
- PNG: **220 dpi**, พื้นขาว

## 3. สัญลักษณ์ (Gane & Sarson แบบที่ใช้ในเล่ม)

| สัญลักษณ์ | รูปทรงและขนาด |
|---|---|
| Process | สี่เหลี่ยมมุมฉาก เส้นดำ **ไม่มีพื้น (NoFill)**; แถบเลขด้านบนสูง **0.32 in** มีเส้นคั่น เลขตัวหนาอยู่กลางแถบ ชื่ออยู่กลางส่วนล่าง; Context: 2.8×4.4 in; L1/L2: กว้าง **PW = 2.0 in** สูงตามจำนวน store/ทางเข้า (ขั้นต่ำ L1 = 2·T0 + (n−1)·DY [+0.12 ถ้ามีทางเข้าด้านข้าง], L2 = max(1.25, 0.95·จำนวน entity + 0.35)) |
| External Entity | สี่เหลี่ยมเส้นดำ ไม่มีพื้น; Context 1.8×0.8 in; L1 สูง **BH = 0.8**, กว้าง `max(1.6, ความกว้างข้อความ@16pt + 0.4)` (พอดีข้อความ ห้ามยืด); L2 สูง 0.8 (0.9 ถ้ามีทั้งเข้าและออก) |
| Entity ซ้ำ | ขีดเฉียงมุมซ้ายบน 0.16 in (ใช้เมื่อจำเป็นต้องวาดซ้ำเพื่อเลี่ยงเส้นตัด) |
| Data Store | เปิดด้านขวา (เส้นบน ซ้าย ล่าง) กว้าง **SW = 2.7** สูง **SH = 0.36** in; ช่องรหัสกว้าง **0.45 in** มีเส้นตั้งคั่น; ไม่มีพื้น |
| Store ซ้ำ | เส้นตั้งเพิ่มที่ 0.07 in จากขอบซ้าย (store ที่ปรากฏมากกว่า 1 ครั้งในรูปเดียว ทุกตัวต้องมีขีดนี้) เลขและชื่อเหมือนเดิม |
| Data Flow | เส้นตรงตั้ง/นอน (orthogonal) หนา **0.75 pt** (LineWeight 0.0104 in) ลูกศรปลาย **EndArrow 13, size 1** (PNG: ยาว 0.11 กว้าง 0.045×2 in หัวทึบ) |

ค่า Visio ที่ **ต้อง** มี (แก้ปัญหากล่องขาวบังตัวอักษร):
- shape ที่เป็น Group (process, store, ตาราง ER) ต้องมี `DisplayMode = 1` (วาด group ไว้ **หลัง** สมาชิก)
  ค่าเริ่มต้นของ Visio คือ 2 = วาด geometry/พื้นของ group **ทับ** สมาชิก ทำให้พื้นขาวบังข้อความและบังสีหัวตาราง
- process / store / entity: `FillPattern = 0` และ geometry `NoFill = 1` (กล่องกลวง ไม่ใช่สีขาว)
- ตรวจด้วย `python templates/tools/check_vsdx.py ไฟล์.vsdx` ทุกครั้ง

## 4. การจัดวาง

### Context
- process 0 กลางหน้า entity ซ้าย-ขวาเป็นคู่แนวนอน (ขาเข้าอยู่สูงกว่าแกน 0.15 in ป้ายอยู่ "above", ขาออกต่ำกว่า 0.15 in ป้าย "below") entity ที่รับอย่างเดียว (เช่น ผู้จัดการ) วางใต้ process ลากแนวตั้ง ป้ายด้านขวา
- ไม่มี Data Store ใน Context

### Level 1 (หน้าเดียว แบบอาจารย์)
- คอลัมน์ process ที่ **XP = 5.6** (กึ่งกลาง) เรียง 1..n จากบนลงล่าง ห่างกัน **0.32 in**
- คอลัมน์ store ที่ **XS = 10.35** แต่ละ process มีแถว store ของตัวเอง ซ้อนลงตามลำดับ `store_order`
  - ช่องว่างต่อแถว: PAD 0.03 + (ป้ายเขียน) + SH + (ป้ายอ่าน) + PAD2 0.05
  - เขียนและอ่าน store เดียวกัน: 2 เส้นขนาน ห่างจากแกนกลาง ±0.2·SH (เขียนบน ป้าย above, อ่านล่าง ป้าย below)
  - store ที่ใช้ร่วมกับ process ก่อนหน้า (`shared_store`): ลากจากใต้กล่อง store เดิมเข้าด้านขวาของ process แทนการวาดซ้ำ
- entity อยู่ซ้าย ขอบซ้าย **EL = 0.3** (เลื่อนได้ด้วย `entity_left` เช่น +0.45 เพื่อหลบเลน)
- ทางเข้าซ้ายของแต่ละ process (`entries`) เรียงจากบนลงล่าง เริ่มที่ T0 = 0.30 ห่าง DY = 0.46 in:
  - `side` = เส้นตรงจากด้านขวาของ entity เข้า process (entity จะวางที่ค่าเฉลี่ย y ของทางเข้า side ของมัน)
  - `lane` = ลงจากใต้กล่อง entity เป็นเลนแนวตั้งแล้วเลี้ยวเข้า process; เลนห่างกัน **0.17 in**; เลนที่เลี้ยวสูงสุดอยู่ขวาสุด (หรือซ้ายสุดเมื่อ `lane_from = left`)
  - `None` = เว้นช่องว่าง 1 ช่อง
  - ป้ายของเส้น entity วางชิดปลายฝั่ง process ห่าง 0.08 in ด้าน above
- เส้นขนานที่ใกล้กันกว่า **0.055 in** ถือว่าทับ จะถูกดันออกเป็นระยะ **0.08 in** (finalize LANE/NEAR)

### Level 2
- entity ที่ **XE = 1.0** (กึ่งกลาง), process ที่ **XP = 6.0**, store ที่ **XS = 11.1**
- sub-process เรียงบนลงล่าง ห่าง 0.85 in; ลูกศรระหว่าง sub-process ลงแนวตั้งกลางกล่อง ป้ายด้านขวา
- entity ของแต่ละ sub-process แบ่งความสูงกล่องเท่าๆ กัน; เข้าและออกคู่เดียวกัน: ±0.2 in
- PAD 0.05 / PAD2 0.07 (โปร่งกว่า Level 1)
- ใช้เลข store และชื่อ entity ชุดเดียวกับ Level 1 เท่านั้น

## 5. ป้าย (label) และเส้น

- ป้ายอยู่บนช่วงเส้นแนวนอนที่ยาวที่สุด กึ่งกลางช่วง: above = ขอบล่างป้ายอยู่เหนือเส้น 0.02 in; เส้นตั้ง: ป้ายด้านขวา 0.04 in
- กล่องป้าย = ความกว้างข้อความ + 0.08 in, สูง = บรรทัด × LINE × 1.05 + 0.04 in
- **ทิศละ 1 ลูกศรต่อคู่** รวมข้อความด้วย "/" หรือ ", " (เช่น "ประวัติสถานะ/อาการชำรุด") ห้ามมี 2 เส้นทิศเดียวกัน
- ห้าม: เส้นตัดกัน, เส้นทับกัน, เส้นผ่านกล่อง, ป้ายทับเส้น/กล่อง, ป้ายทับป้าย
  finalize ต้องรายงาน `{'overlap': 0, 'cross': 0, 'through_shape': 0, 'label_hits': 0, 'label_label': 0}`
- เส้นเข้าออกที่ด้านซ้าย/ขวาเป็นหลัก ใช้ด้านบน/ล่างเฉพาะเส้นตั้ง

## 6. การตั้งชื่อ

- process = วลีกริยา: "จัดการข้อมูลอุปกรณ์", "แจกจ่ายอุปกรณ์ให้ช่าง", "บันทึกการใช้งานและปรับสถานะอุปกรณ์"
- store = "ข้อมูล..." หรือ "ประวัติ..." (คำนาม) ใช้รหัส D1..Dn เดิมทุก level
- data flow = คำนาม: "ข้อมูล...", "รายการ...", "รายงาน...", "สถานะ..."
- ตัดบรรทัดชื่อ process เอง (`process_breaks`) ที่ขอบคำ เช่น `แจกจ่าย\nอุปกรณ์ให้ช่าง`
- ใช้คำเดียวต่อหนึ่งสิ่งทั้งเล่ม (เช่น "ชำรุด" ไม่ใช่ "เสีย", "ทีม" ไม่ใช่ "สายงาน")

## 7. เมื่อไรต้องมี Level 2

- process ที่มีหลายขั้นตอนต่อกัน (ผลของขั้นหนึ่งเป็นข้อมูลเข้าของขั้นถัดไป) มีหลายผู้กระทำ หรือเขียนหลาย store
- ตัวอย่าง: 6.0 (บันทึกการใช้งาน → ปรับสถานะ/อาการชำรุด → รับคืนและส่งซ่อม) และ 8.0 (คำนวณระยะเวลา → ตรวจเกณฑ์ KPI/แจ้งเตือน → ออกรายงาน)
- process แบบบันทึก/แก้ไขขั้นเดียว (1.0–4.0, 7.0) ไม่ต้องแตก
- Balancing ตรวจโดย `d_l2.check_balance` และ `tools/check_spec.py`

## 8. รูปแบบที่ห้าม

| ชื่อ | ลักษณะ | วิธีแก้ |
|---|---|---|
| Black hole | process มีแต่ข้อมูลเข้า | เพิ่มข้อมูลออก (store หรือรายงาน) หรือตัด process |
| Miracle | process มีแต่ข้อมูลออก | หาข้อมูลเข้าที่ใช้สร้างผลลัพธ์ |
| Gray hole | ข้อมูลออกสร้างจากข้อมูลเข้าไม่ได้ | เพิ่ม store/flow ที่ให้ข้อมูลนั้น |
| Entity ↔ Store | entity เขียน/อ่าน store ตรง | ผ่าน process เสมอ |
| Store ↔ Store | store ส่งข้อมูลถึงกันตรง | ผ่าน process เสมอ |
| Entity ↔ Entity | คนส่งข้อมูลถึงกันโดยไม่ผ่านระบบ | ไม่ต้องวาด (อยู่นอกระบบ) |
| 2 ลูกศรทิศเดียวกัน | คู่เดียวกันมีหลายเส้นทางเดียวกัน | รวมเป็นเส้นเดียว รวมป้าย |
| สถานะเป็น process | "ส่งซ่อม", "ชำรุด" เป็นกล่อง | ใช้ process "ปรับสถานะ" + ตาราง lookup |

## 9. สไตล์อาจารย์ (ที่ผ่านการตรวจแล้ว)

- Level 1 อยู่ในหน้าเดียว process เรียงเป็นคอลัมน์เดียวตามลำดับการเกิดข้อมูล store อยู่ขวา entity อยู่ซ้าย
- กล่อง process มีเลขเสมอ (1..8 ใน L1, 6.1.. ใน L2) กล่อง entity พอดีข้อความ ไม่ยืดยาว
- เรียบ ขาวดำ กล่องกลวง ไม่มีเงา ไม่มีสีใน DFD (สีมีที่เดียวคือหัวตาราง ER)
- Context ใช้ชื่อข้อมูลสรุป ไม่ลงรายละเอียดเท่า Level 1
