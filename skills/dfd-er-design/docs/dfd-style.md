# DFD style (Context, Level 1, Level 2): ค่าที่ใช้จริง

ทุกค่ามาจาก `templates/generator` (draw.py, lay.py, vsdx.py, d_*.py) ที่สร้างรูปในรายงานจริง
**อย่าเดาค่าใหม่ ให้คัดลอก template แล้วแก้ spec** ถ้าต้องเปลี่ยนค่า ให้แก้ใน spec (`layout`) ไม่ใช่ในโค้ด

## 2. หน้ากระดาษ

- **1 แผนภาพ = 1 หน้า Visio = 1 รูป** ห้ามแบ่ง Level 1 เป็นหลายหน้า
- canvas เริ่มต้น: Context 12.4×10.2, Level 1 13×20, Level 2 13×12 (นิ้ว) แล้ว `fit()` ตัดขอบให้เหลือ margin **0.12 in** รอบรูป
- PageScale = DrawingScale = 1 in (1:1)
- ขนาดหลัง fit ของตัวอย่าง: Context 12.44×7.49, L1 11.64×21.05, L2-P6 12.49×7.81, L2-P8 12.51×9.17 นิ้ว
- PNG: **220 dpi**, พื้นขาว

## 3. สัญลักษณ์ (Gane & Sarson แบบที่ใช้ในเล่ม)

| สัญลักษณ์ | รูปทรงและขนาด |
|---|---|
| Process | สี่เหลี่ยมมุมฉาก เส้นดำ **ไม่มีพื้น (NoFill)**; แถบเลขด้านบนสูง **0.32 in** มีเส้นคั่น เลขตัวหนาอยู่กลางแถบ ชื่ออยู่กลางส่วนล่าง; Context: 2.8×4.4 in; L1/L2: กว้าง **PW = 2.0 in** สูงตามจำนวน store/ทางเข้า (ขั้นต่ำ L1 = 2·T0 + (n−1)·DY [+0.12 ถ้ามีทางเข้าด้านข้าง], L2 = max(1.25, 0.95·จำนวน entity + 0.35)) |

| Entity ซ้ำ | ขีดเฉียงมุมซ้ายบน 0.16 in (ใช้เมื่อจำเป็นต้องวาดซ้ำเพื่อเลี่ยงเส้นตัด) |
| Data Store | เปิดด้านขวา (เส้นบน ซ้าย ล่าง) กว้าง **SW = 2.7** สูง **SH = 0.36** in; ช่องรหัสกว้าง **0.45 in** มีเส้นตั้งคั่น; ไม่มีพื้น |
| Store ซ้ำ | เส้นตั้งเพิ่มที่ 0.07 in จากขอบซ้าย (store ที่ปรากฏมากกว่า 1 ครั้งในรูปเดียว ทุกตัวต้องมีขีดนี้) เลขและชื่อเหมือนเดิม |
| Data Flow | เส้นตรงตั้ง/นอน (orthogonal) หนา **0.75 pt** (LineWeight 0.0104 in) ลูกศรปลาย **EndArrow 13, หัวเล็ก EndArrowSize 0** (PNG: ยาว 0.075 กว้าง 0.03×2 in หัวทึบ) ตั้งแต่ v3.3; เล่มระบบอะไหล่ที่ส่งแล้วใช้ `"arrow": "legacy"` (size 1, PNG 0.11) |

ค่า Visio ที่ **ต้อง** มี (แก้ปัญหากล่องขาวบังตัวอักษร):
- shape ที่เป็น Group (process, store, ตาราง ER) ต้องมี `DisplayMode = 1` (วาด group ไว้ **หลัง** สมาชิก)
  ค่าเริ่มต้นของ Visio คือ 2 = วาด geometry/พื้นของ group **ทับ** สมาชิก ทำให้พื้นขาวบังข้อความและบังสีหัวตาราง
- process / store / entity: `FillPattern = 0` และ geometry `NoFill = 1` (กล่องกลวง ไม่ใช่สีขาว)
- ตรวจด้วย `python templates/tools/check_vsdx.py ไฟล์.vsdx` ทุกครั้ง

## 4. การจัดวาง

### Context
- **ลูกศรทุกเส้นต้องติดขอบกล่อง process 0 และขอบกล่อง entity ทั้งสองปลาย** (ห้ามเริ่ม/จบกลางที่ว่าง) entity ที่อยู่ซ้าย-ขวาต้องอยู่ในช่วงความสูงของกล่อง 0;
  generator ขยายกล่อง 0 ให้ครอบทุกเส้นเอง และหยุดทำงาน (ValueError) ถ้ามีปลายเส้นที่ไม่อยู่บนขอบกล่อง
- process 0 กลางหน้า entity ซ้าย-ขวาเป็นคู่แนวนอน (ขาเข้าอยู่สูงกว่าแกน 0.15 in ป้ายอยู่ "above", ขาออกต่ำกว่า 0.15 in ป้าย "below") entity ที่รับอย่างเดียว (เช่น ผู้จัดการ) วางใต้ process ลากแนวตั้ง ป้ายด้านขวา
- ไม่มี Data Store ใน Context

### กฎเหล็ก: ห้ามเส้นตัดกัน และห้ามเส้นค่อม/กระโดดข้าม (line jump) ทุกรูป
- เส้นสองเส้นห้ามตัด ห้ามแตะ ห้ามทับกัน และ **ห้ามใช้ line jump (เส้นโค้งค่อมข้าม)** ทั้งใน PNG และ Visio (หน้า Visio ตั้ง LineJumpCode = 0)
- เส้นห้ามผ่านกล่องใด ๆ (รวมกล่องปลายเส้นของตัวเอง) และห้ามผ่านป้ายของเส้นอื่น
- ถ้าจะชนกัน ให้ **อ้อมไปด้านหลัง** (ไปช่องเส้นตั้งที่อยู่ไกลกว่า อ้อมรอบกลุ่มเส้นด้านใน) หรือย้ายตำแหน่ง store
  ถ้าอ้อมแล้วยังเป็นไปไม่ได้ทางคณิตศาสตร์ จึงวาด store ซ้ำ (ไม่เกิน 1 สำเนาต่อตัว มีขีดซ้ำ)
- `build.py` หยุดทำงานถ้า finalize รายงาน `cross` > 0 และ `tools/check_vsdx.py` FAIL ทุกคู่ connector ที่ตัด/แตะกัน
  และทุก connector ที่ผ่านกล่องหรือป้าย

### Level 1 แบบ store เดียว (`"store_mode": "single"`, ค่าเริ่มต้นของงานใหม่) ไม่มีเส้นตัดโดยโครงสร้าง
- process เรียงเป็นคอลัมน์เดียว entity อยู่ซ้าย store อยู่ขวา เส้น process→store ออกขอบขวาของ process เป็นเส้นนอน (ป้ายอยู่เหนือเส้นชิด process)
  → ลงช่องเส้นตั้งของตัวเอง (ห่างกัน `lane_step_r` 0.14 in) → เข้าขอบซ้ายของ store
- **กลุ่มเส้นซ้อนกันแบบ "อ้อมไปด้านหลัง"**: store ที่ใช้โดย process ช่วงกว้างอยู่คอลัมน์ไกลกว่า (ขวากว่า) และเส้นของมันอ้อมรอบกลุ่มที่อยู่ในช่วงแคบกว่า
  ระดับคอลัมน์ = 1 + ระดับสูงสุดของกลุ่มที่อยู่ข้างใน คอลัมน์ห่างกัน `store_gap` 0.35 in เส้นบนสุดใช้ช่องขวาสุด (เส้นล่างก็เช่นกัน) จึงไม่ตัดกันเลย
- store วางที่กึ่งกลางพอร์ตของกลุ่ม (จำนวนเส้นคี่ = เส้นกลางตรง) ระยะพอร์ตบน store `store_port_step` 0.16 in
- **จำนวนสำเนาน้อยที่สุดที่ไม่มีเส้นตัด**: generator ค้นทุกแบบ เริ่มจาก 0 สำเนา แล้ว 1, 2, ... (ไม่เกิน 1 สำเนาต่อ store) และเลือกแบบที่ไม่มีเส้นตัด
  ที่หน้ากว้างน้อยและเส้นสั้นที่สุด ถ้าทำไม่ได้จะ error (ห้ามยอมให้ตัด)
  - process ที่อ่านทุก store (เช่น ออกรายงาน) มักต้องใช้สำเนา store ข้าง ๆ ตัวมันเอง
  - ตัวอย่างจองสนาม: พิสูจน์ด้วยการค้นทุกแบบแล้วว่า 3 สำเนาคือน้อยที่สุดสำหรับ process คอลัมน์เดียว แม้ให้อ้อมไปซ้าย/อ้อมหลังได้
  - กล่องทุกกล่องของ store ที่ซ้ำต้องมีขีดซ้ำ (เส้นตั้งที่ 0.07 in ในช่องรหัส)
  - กำหนดเองได้: `"duplicates": "none"` (ห้ามซ้ำ: error ถ้าเป็นไปไม่ได้) หรือ `{"D4": ["7.0", "8.0"]}` (process ที่ใช้สำเนาที่ 2 ต้องไม่ตัดกัน)
- **entity กล่องเดี่ยวก่อนเสมอ** ด้านซ้าย วางเยื้องตามลำดับ process แรกที่ใช้ (`entity_step` 2.4 in: ตัวแรกซ้ายสุด/บนสุด)
  เส้นตรงเข้า process แรก (side) ที่เหลือลงจากใต้กล่องเป็นรูป L ซ้อนกัน (lane ห่าง 0.18 in, process ไกลกว่าใช้ lane ซ้ายกว่า)
  ซ้อนกันได้โดยไม่ตัดเมื่อชุด process ของแต่ละ entity ไม่สลับกัน (ไม่ interlace); ใน process เดียวกัน เส้นที่ลงมาจากด้านบนอยู่บน
  (entity ในกว่าอยู่บนสุด) แล้วจึงเป็น entity ที่กล่องอยู่ข้าง process นั้น
- ซ้ำ entity เป็น **ทางสุดท้าย** เฉพาะเมื่อชุด process สลับกันจนตัดแน่นอน: ไม่เกิน 1 สำเนา มีขีดเฉียงมุมซ้ายบน (generator ค้นหาให้เอง)
- ระยะห่างพอร์ตบน process = ความสูงป้าย + `port_pad` 0.12 in (ให้เส้นห่างกล่อง store ข้างเคียงพอ)
- ตัวเลือกอื่นใน spec (ไม่ต้องใส่ก็ได้): `entries`/`entity_order`/`entity_left`/`lane_from` (ถ้าไม่ใส่ จะสร้างให้: process แรกของ entity = side, ที่เหลือ = lane),
  `XP`, `process_gap` 0.36, `min_process_h` 1.0; ตัวอย่างเต็ม `examples/booking/booking.json`
- ข้อแลก: หน้ากว้างขึ้นเพราะมีหลายคอลัมน์ store (ตัวอย่างจองสนาม 23.2 x 17.9 in) ย่อลงหน้ากระดาษตาม `docs/report-insertion.md`

### Level 1 แบบหน้าแคบ `"layout": "column-rails"` (ทางเลือก ไม่ใช่ค่าเริ่มต้น: ผู้ใช้ไม่เลือกแบบนี้ เพราะซ้ำ entity)
- process คอลัมน์เดียว entity คอลัมน์ซ้าย store คอลัมน์ขวา กล่อง entity/store วางข้าง process ที่ใช้มากที่สุด (เส้นตรงแนวนอน)
- เส้นไป process อื่นวิ่งใน **ราง (rail) แนวตั้งขนานกัน** ด้านนอกคอลัมน์กล่อง: store ออกขอบบน/ล่าง (กล่องยืดไปถึงรางของตัวเอง +0.04 in),
  entity ออกขอบซ้าย แล้วเข้าข้าง process เป็นเส้นนอนระหว่างกล่องอื่น รางที่ล้อมพอร์ต/กล่องของเส้นอื่นอยู่ไกลกว่า (ห่าง `rail_step` 0.1 in) จึงไม่ตัดกัน
- generator เริ่มจากกล่องข้าง process ทุกตัว (ไม่มีราง) แล้วรวมสำเนาทีละคู่ที่เพิ่มความยาวรางน้อยที่สุด ตราบที่ยังไม่ตัดกันและหน้ากว้าง ≤ `max_width` 6.0 in
- จึงซ้ำ entity/store ได้หลายกล่อง (ทุกกล่องที่ซ้ำมีขีดซ้ำ) ตรวจด้วย `check_vsdx.py --max-copies 0`; เส้นตัด 0 ไม่มี line jump เหมือนเดิม
- ค่าเริ่มต้น: label_pt 8 (= TH Sarabun ~12 pt จริง), PPT 9, SPT 8, EPT 9, ป้ายยาวเกิน `max_label_w` 0.9 in ตัดเป็น 2 บรรทัด, ชื่อ store เกิน 0.75 in ตัดบรรทัด
- ยังไม่รองรับเส้น process ↔ process (generator จะหยุดและบอก); ตัวอย่าง `examples/booking/booking_rails.json`

### Level 1 แบบเดิม (`store_order`, store ข้าง process ทุกตัว) ใช้กับเล่มระบบอะไหล่ที่ส่งแล้วเท่านั้น
- เป็นสไตล์ของรูปในเล่มที่ผ่านอาจารย์แล้ว (store ซ้ำหลายกล่อง) generator ยังสร้างได้เพื่อแก้เล่มเดิม แต่ **งานใหม่ห้ามใช้** check_spec จะเตือน
- คอลัมน์ process ที่ **XP = 5.6** (กึ่งกลาง) เรียง 1..n จากบนลงล่าง ห่างกัน **0.32 in**
- คอลัมน์ store ที่ **XS = 10.35** แต่ละ process มีแถว store ของตัวเอง ซ้อนลงตามลำดับ `store_order`
  - ช่องว่างต่อแถว: PAD 0.03 + (ป้ายเขียน) + SH + (ป้ายอ่าน) + PAD2 0.05
  - เขียนและอ่าน store เดียวกัน: 2 เส้นขนาน ห่างจากแกนกลาง ±0.2·SH (เขียนบน ป้าย above, อ่านล่าง ป้าย below)
  - store ที่ใช้ร่วมกับ process ก่อนหน้า (`shared_store`): ลากจากใต้กล่อง store เดิมเข้าด้านขวาของ process แทนการวาดซ้ำ
- entity อยู่ซ้าย ขอบซ้าย **EL = 0.3** (เลื่อนได้ด้วย `entity_left` เช่น +0.45 เพื่อหลบเลน)
- ทางเข้าซ้ายของแต่ละ process (`entries`) เรียงจากบนลงล่าง เริ่มที่ T0 = 0.30 ห่าง DY = 0.46 in:
  - `side` = เส้นตรงจากด้านขวาของ entity เข้า process (entity จะวางที่ค่าเฉลี่ย y ของทางเข้า side ของมัน)
  - `lane` = ลงจากใต้กล่อง entity เป็นเลนแนวตั้งแล้วเลี้ยวเข้า process; เลนห่างกัน **0.17 in**; เลนที่เลี้ยวสูงสุดอยู่ขวาสุด (หรือซ้ายสุดเมื่อ `lane_from = left`)
  - `None` = เว้นช่องว่าง 1 ช่อง
  - ป้ายของเส้น entity วางชิดปลายฝั่ง process ห่าง 0.08 in ด้าน above
- เส้นขนานที่ใกล้กันกว่า **0.055 in** ถือว่าทับ จะถูกดันออกเป็นระยะ **0.08 in** (finalize LANE/NEAR)

### Level 2
- entity ที่ **XE = 1.0** (กึ่งกลาง), process ที่ **XP = 6.0**, store ที่ **XS = 11.1**
- sub-process เรียงบนลงล่าง ห่าง 0.85 in; ลูกศรระหว่าง sub-process ลงแนวตั้งกลางกล่อง ป้ายด้านขวา
- entity ของแต่ละ sub-process แบ่งความสูงกล่องเท่าๆ กัน; เข้าและออกคู่เดียวกัน: ±0.2 in
- PAD 0.05 / PAD2 0.07 (โปร่งกว่า Level 1)
- ใช้เลข store และชื่อ entity ชุดเดียวกับ Level 1 เท่านั้น

## 5. ป้าย (label) และเส้น

- **กฎเหล็ก: ทุกเส้นต้องติดกับรูปทั้งสองปลาย** เป็น Visio connector จริง (มี BeginX/EndX) ที่ glue กับ connection point บนขอบกล่อง
  (`<Connect FromCell='BeginX'/'EndX' ToCell='Connections.Xn'>`) ห้ามวาดเส้นหรือลูกศรลอยๆ ที่แค่วางชิดกล่อง และปลายเส้นต้องอยู่บนขอบกล่องจริง (คลาดได้ไม่เกิน 0.02 in)
  `tools/check_vsdx.py` จะ FAIL ถ้ามีปลายเส้นไม่ glue, glue กับจุดที่ไม่มี/ไม่อยู่บนขอบ, ปลายเส้นไม่อยู่บนขอบรูป หรือมีรูปลูกศรที่ไม่ใช่ connector
- ป้ายอยู่บนช่วงเส้นแนวนอนที่ยาวที่สุด กึ่งกลางช่วง: above = ขอบล่างป้ายอยู่เหนือเส้น 0.02 in; เส้นตั้ง: ป้ายด้านขวา 0.04 in
- กล่องป้าย = ความกว้างข้อความ + 0.08 in, สูง = บรรทัด × LINE × 1.05 + 0.04 in
- **ทิศละ 1 ลูกศรต่อคู่** รวมข้อความด้วย "/" หรือ ", " (เช่น "ประวัติสถานะ/อาการชำรุด") ห้ามมี 2 เส้นทิศเดียวกัน
- ห้าม: เส้นตัดกัน, เส้นทับกัน, เส้นผ่านกล่อง, ป้ายทับเส้น/กล่อง, ป้ายทับป้าย
  finalize ต้องรายงาน `{'overlap': 0, 'cross': 0, 'through_shape': 0, 'label_hits': 0, 'label_label': 0}` ไม่มีข้อยกเว้น (ห้าม line jump)
- เส้นเข้าออกที่ด้านซ้าย/ขวาเป็นหลัก ใช้ด้านบน/ล่างเฉพาะเส้นตั้ง

## 6. การตั้งชื่อ

- process = วลีกริยา: "จัดการข้อมูลอุปกรณ์", "แจกจ่ายอุปกรณ์ให้ช่าง", "บันทึกการใช้งานและปรับสถานะอุปกรณ์"
- store = "ข้อมูล..." หรือ "ประวัติ..." (คำนาม) ใช้รหัส D1..Dn เดิมทุก level
- data flow = คำนาม: "ข้อมูล...", "รายการ...", "รายงาน...", "สถานะ..."
- ตัดบรรทัดชื่อ process เอง (`process_breaks`) ที่ขอบคำ เช่น `แจกจ่าย\nอุปกรณ์ให้ช่าง`
- ใช้คำเดียวต่อหนึ่งสิ่งทั้งเล่ม (เช่น "ชำรุด" ไม่ใช่ "เสีย", "ทีม" ไม่ใช่ "สายงาน")

## 7. เมื่อไรต้องมี Level 2

- process ที่มีหลายขั้นตอนต่อกัน (ผลของขั้นหนึ่งเป็นข้อมูลเข้าของขั้นถัดไป) มีหลายผู้กระทำ หรือเขียนหลาย store
- ตัวอย่าง: 6.0 (บันทึกการใช้งาน → ปรับสถานะ/อาการชำรุด → รับคืนและส่งซ่อม) และ 8.0 (คำนวณระยะเวลา → ตรวจเกณฑ์ KPI/แจ้งเตือน → ออกรายงาน)
- process แบบบันทึก/แก้ไขขั้นเดียว (1.0–4.0, 7.0) ไม่ต้องแตก
- Balancing ตรวจโดย `d_l2.check_balance` และ `tools/check_spec.py`

## 8. รูปแบบที่ห้าม

| ชื่อ | ลักษณะ | วิธีแก้ |
|---|---|---|
| Black hole | process มีแต่ข้อมูลเข้า | เพิ่มข้อมูลออก (store หรือรายงาน) หรือตัด process |
| Miracle | process มีแต่ข้อมูลออก | หาข้อมูลเข้าที่ใช้สร้างผลลัพธ์ |
| Gray hole | ข้อมูลออกสร้างจากข้อมูลเข้าไม่ได้ | เพิ่ม store/flow ที่ให้ข้อมูลนั้น |
| Entity ↔ Store | entity เขียน/อ่าน store ตรง | ผ่าน process เสมอ |
| Store ↔ Store | store ส่งข้อมูลถึงกันตรง | ผ่าน process เสมอ |
| Entity ↔ Entity | คนส่งข้อมูลถึงกันโดยไม่ผ่านระบบ | ไม่ต้องวาด (อยู่นอกระบบ) |
| 2 ลูกศรทิศเดียวกัน | คู่เดียวกันมีหลายเส้นทางเดียวกัน | รวมเป็นเส้นเดียว รวมป้าย |
| สถานะเป็น process | "ส่งซ่อม", "ชำรุด" เป็นกล่อง | ใช้ process "ปรับสถานะ" + ตาราง lookup |

## 9. สไตล์อาจารย์ (ที่ผ่านการตรวจแล้ว)

- Level 1 อยู่ในหน้าเดียว process เรียงเป็นคอลัมน์เดียวตามลำดับการเกิดข้อมูล store อยู่ขวา entity อยู่ซ้าย
  (เล่มระบบอะไหล่ใช้แบบ store ข้าง process; งานใหม่ตามที่ผู้ใช้กำหนด 5 พ.ย. 2569: store วาดครั้งเดียวแล้วลากเส้นเข้า ซ้ำเฉพาะเมื่อจำเป็น)
- กล่อง process มีเลขเสมอ (1..8 ใน L1, 6.1.. ใน L2) กล่อง entity พอดีข้อความ ไม่ยืดยาว
- เรียบ ขาวดำ กล่องกลวง ไม่มีเงา ไม่มีสีใน DFD (สีมีที่เดียวคือหัวตาราง ER)
- Context ใช้ชื่อข้อมูลสรุป ไม่ลงรายละเอียดเท่า Level 1
